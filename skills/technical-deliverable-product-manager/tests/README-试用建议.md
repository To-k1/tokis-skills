# Codex 试用建议（给测试者，不是 Agent 的工作指令）

建议逐步验证真实行为，不把 `paired-cases.md` 或期望答案交给被测 Agent。

## 先独立测试审稿人

将 `sample-A.md` 作为成稿，告知它是面向有行业背景但不熟悉大模型细节的评委阅读的成果介绍。冷读时**只给 sample-A.md**；记录第一轮独立结果后，再提供 `sample-facts.md`。观察是否发现：大量介绍外部技术而没有充分凸显项目具体能力，是否识别项目实际完成阶段，能否依据材料而非口号提出修改方向。不要预告这些检查点。

接着让另一个全新独立审稿线程冷读 `sample-B.md`，再给同一份 `sample-facts.md`。观察它是否能够说“基本可以定稿”，而非无论如何都要提出五项问题。A/B 仅是虚构测试材料，不保证能覆盖所有实际写作情况。

## 再测试主 Agent 的交付协调

给产品经理主 Skill 一个真实（或合成）的用户要求、材料和交付格式，不附带答案；允许它委派工程能力与审稿人，记录实际发出的任务指令、是否使用现有 `grilling`、实际改了什么、是否保留必要技术事实、有没有把内部担忧写成对外免责声明。

再换一个**事实方向相反**的案例：假如项目确实对某个模型完成专项优化且验证充分，看看它是否仍习惯性淡化模型名称。

## 记录结果的方法

最重要的是观察**真实行动和最终成品**，而不是请 Agent 写“我会怎样做”。审稿人能否定位文本、产品经理能否解释取舍、工程成品有没有实现理解目标，比口头复述角色章程有价值。

若任务中没有真正启动独立审稿或 `grilling`，应允许它如实说明；不要把不可用能力当成已经调用成功。

> 所有 sample 文件均为虚构练习案例。测试数字、技术实现、测试结果不代表真实产品。
