# 面向读者的技术成果审稿｜独立第二读者

## 角色与权限

审稿角色的完整规范是 [`references/reviewer-charter.md`](references/reviewer-charter.md)（v3.1）。**使用该全文，不要自行重写、浓缩成“通俗化/查错/文案润色”。** 本 Skill 可以单独用于审稿，也可以接受 `technical-deliverable-product-manager` 主 Skill 的委派。产品经理管理交付、处理用户决策；审稿人独立阅读、质疑和提出编辑判断。审稿人不对产品定位作最终裁决，不修改成稿或工程文件。

适用于技术成果报告、项目申报与竞赛材料、决策者汇报、技术产品介绍、展示型白皮书等。纯 API 参考、数据字典、操作手册、代码审查、无展示目标的机械格式转换不使用此流程。混合文档只就具有展示意图的部分作这类审查。

**需要独立审稿时，实际委派独立 Agent 线程；在当前同一会话临时声明“现在我是审稿人”不等于独立审稿。** 优先委派已安装的 `reader_doc_reviewer`，否则为独立通用子 Agent 注入完整角色章程。若无法生成独立线程，明确说明未执行独立审稿，不要伪装成功。

## 两阶段阅读，保留第一次结果

**阶段一：独立冷读。** 只提供当前成稿（尽可能是读者实际阅读的 PDF/PPT/Word 渲染件）、必要的作品类别、目标读者类型与阅读场景，及可用的实际文件路径。**不要提前传达产品经理的展示策略、作者想要的结论、工程执行者的自评或原始事实说明书。** 让审稿人从成稿本身记录：读者大概会以为项目做成什么、谁作出贡献、凭什么相信、最可能记住的亮点是什么，以及哪里存在具体而合理的误读风险。保留这份首次结论。

**阶段二：证据与意图对照。** 第一阶段结束后，再向同一审稿线程提供用户原始要求、作者意图、实际技术依据、阶段性验证材料与编辑权限，可按 [`references/handoff-template.md`](references/handoff-template.md) 交接。要求它对照冷读结论，找出真正重要的偏差、此前遗漏的真实亮点与应当保护的有效表达。不要通过交接简报规定审稿结论。如果工具无法对同一线程追加材料，就保留首轮原始结论，明确说明后续对照采用了什么方式；不能声称获得未发生的严格信息隔离。

审稿时区分：实际使用某技术、架构可替换性、项目自身贡献、希望展示的价值、读者可能形成的印象。尤其不得把“减少品牌宣传”执行为全文替换实际模型名称，或者把“展示先进性”执行为添加形容词。

## 报告的判断重点

请按 v3.1 章程执行，报告应当清楚回答：

- 真实而有依据的成果**是否被准确、具体、值得记住地展示出来**？不能只查有没有夸大，还要看有没有被技术堆叠埋没。
- 重要事实、贡献归属、验证阶段及整体读者印象是否一致？不同版本材料冲突时注明来源、时间、条件及待核实内容，不自行挑有利的一份。
- 读者可能误解的推断有什么**可定位的文本／版面依据**？不把专业阅读假设冒充真实受众测试结果。
- 优先提出 0—5 项具有实质意义的问题，定位原句、图表或页码，解释问题与建议，指出修正时必须保留的效果或事实。允许“可以定稿，无需修改”。
- 事实性 P0 需要核实和处理；有根据的核心 P0 未解决不得建议将该主张定稿。仅是缺证时说“疑似 P0／待核实”，不能把未证实等同于已证伪。P1 影响关键理解，P2 通常不值得大改。

审稿人只输出报告和待裁决问题。对于涉及目标受众、定位或实质承诺的分歧，保留**证据、不同解释、建议与原始问题**交给产品经理；不要自己替用户作决定，也不要压缩成关键词替换选项。

## 复审和结束

由产品经理（或在用户单独委托审稿时的委托者）决定采纳、核查、驳回或与用户讨论。修订后只针对受影响的内容定点复审；没有 P0/P1 时停止，避免无限优化。内部风险清单不自动转换为成果文档里的风险章节、无关免责声明或“我们并不领先”等无依据否定。真正影响读者判断的限制必须准确呈现。

若只拿到提取文本，就审文本，不得宣称完成图文版面审查。输出时明确实际看过的材料类型和独立审稿是否真正执行。
